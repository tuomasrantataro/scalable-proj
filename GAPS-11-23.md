## 2. Reported latency leaves out the 60 s wait

**Fixed on 24 Nov 2026:** the default of `OUT_OF_ORDERNESS_S` is 1 s instead of 60 s (job, `docker-compose.yml`, reference
and `compare.py`), and the delay from the window's end is measured. Details in [`MEASUREMENTS.md`](MEASUREMENTS.md) §8.

- **Correctness:** full week with 60, 5, 1, 0.5 and 0 s: reference digest and 5,506 late events in every run; 1 and 0.5 s also in
  live runs, bit for bit, 73 of 73 advisories delivered. The new default was run once more and compared bit for bit.
- **Delay, window end → advisory received, at real-time pace (p50):** 60.7 s (D = 60), 5.6 s (5), 1.65 s (1). One run each,
  two window closes. 0.5 s cannot be measured with this feed: `Time` has whole seconds, so the replay sends events up to
  1 s early.
- **Remaining, not part of the fix:** 0.5–0.6 s above the bound, only partly explained (200 ms watermark interval; maybe
  `fetch.min.bytes`, not tested); whether 1 s raises the live p95 of `fired → received` is open: 0.85–1.7 s in 6 live runs
  at 1 or 0.5 s against 0.8 s in the one run at 60 s (`MEASUREMENTS.md` §8, §9). With 1 s, a partition silent for `IDLENESS_S` (10 s) has less cushion.
- **In the report:** state what the latency includes and give the time from the window's end. Repeat with
  `bench/window_delay.py` (A8).

## 9. Scaling limited by the TimescaleDB writer

**Fixed on 24 Nov 2026**, with one database on one host. Details in [`MEASUREMENTS.md`](MEASUREMENTS.md) §12, script `bench/db_limit.py`.

- **Faster writer:** `reWriteBatchedInserts=true` is now in the default `JDBC_URL`. Full week from the stored backlog, 3 alternating runs each:
  121–127 s → 82–84 s, writer busy 88–92% → 43–45%, reference digest in all runs, failover tested (2 kills, reference digest).
- **Realistic traffic is no problem:** at real time around the week's busiest minute each close (3,089 rows) is stored within 1.2 s of the 300 s
  available; writer busy 0.0%, no backpressure. At the producer's maximum (1.15 M events/s) the writer is busy 7% and nothing waits.
- **Where it becomes the limit:** about 50,000 rows/s (4 writers; with the 40,000-symbol mix 0.63 M instead of 1.63 M events/s). Rows per close: EMA
  results begin to wait between 10,000 and 20,000 (the real feed has about 3,100). In events/s it depends on the mix: about 0.6 M with 40,000
  equal symbols, about 8 M (extrapolated) for the real mix, more than the job reads.
- **Remaining:** one run per point (two for the week); the parallelism 8 result was not repeated (A6); why the writers saturate (four synchronous
  connections or the server itself) is not separated.
- **Repeat in part A:** A10b (about 95 min). All measurements before §12 used the old setting, so part A has to run on the new one.

## Not gaps, but to be stated in the report

- **The reference has the same author and interpretations as the job.** It finds coding errors, not shared
  misreadings. Justify the two decisions that change the results: empty windows are skipped, and zero prices are excluded
  (11,349 advisories instead of 25,834; both variants are computed by the reference).
- **Initialization:** 4,970 of the 11,349 advisories (44%) are the first BUY of a symbol, caused by EMA = 0. They are
  flagged `initial`.
- **Only advisories are delivered per trader.** EMA values are available for every symbol in TimescaleDB and Grafana
  (relaxation 3 of the project description asks for updates for the subscribed symbols).
- **Limits:** one host, one broker, one database. A new job starts with EMA = 0 (no savepoints scripted). No GPU is used.
